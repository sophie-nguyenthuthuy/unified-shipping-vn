# 0002. Postgres + Prisma as system of record

Status: **accepted**
Date: 2026-05-14

## Context

We have transactional needs (shipment creation must atomically write a `shipments` row and an `expected` COD ledger entry), strong consistency requirements on tenant boundaries, and a heavy reporting/aggregation workload (reconciliation, dashboards). We do not need full-text search at this scale, and we don't need horizontal write scaling.

## Decision

Postgres 16. Prisma as the ORM and migration tool. All durable state lives here. Redis is a cache + queue, not a source of truth.

## Consequences

- We use Postgres for what it's good at: JSONB on `pickup` / `delivery` / `parcel` for flexibility, integer minor units for money, partial indexes on hot paths (`(merchantId, status)`), shadow DB in CI to catch migration footguns.
- Prisma's relation queries replace most of what we'd otherwise hand-write. Where we need raw SQL (rare), we use `$queryRaw` with template tags so types stay sound.
- We accept Prisma's lock-in: schema is in `schema.prisma`, not in handwritten SQL. The migration files generated by Prisma are checked in and auditable.

## Alternatives considered

- **Drizzle**: smaller runtime, but less mature migration story and weaker type inference for our nested writes.
- **TypeORM**: rejected; too many footguns.
- **DynamoDB / Mongo**: rejected. Our access patterns are deeply relational (joining shipments to ledger entries to remittance lines).
